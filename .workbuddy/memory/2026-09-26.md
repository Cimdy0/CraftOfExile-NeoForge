
## 族数据去重复：BonusFamily 最终形态 `Map<AffixKey, List<TierBonus>>`（BUILD SUCCESSFUL）
- 用户定调：「不仅是 build() 的问题，记录类或者说 json 的架构也需要改变，避免重复的数据」；
  最终形态 `Map<A, List<B>>`，A = 装备部位 × 可空落位，B = 值侧一格（词缀 + 幅度 + 阶）。
- **词缀最终放在值里、不在键里**（用户定调）：「把 AdditionType 直接存入值里，恰巧精髓第四阶会改变，
  这一点同时符合精髓和符文的构造」。于是：
  - `AffixKey` 收窄为 `(String branch, Optional<Location> location)`，编码 `部位~落位`（无落位写 `-`）；
  - `TierAmount(min,max,tier)` → **`TierBonus(AdditionType type, double min, double max, Tier tier)`**
    （词缀进值），`TierAmount.java` 已删；`TieredBonus.java` 更早已删。
  - 精髓「第四阶换词缀」与符文「第四阶只换数值」因此同一件事：一格 = 一阶，键不变；
    同位置同阶并列多条词缀 = 一格里两条，键不膨胀。
- `BonusFamily.ladders` 取代旧 `Map<String, List<Bonus>>`；JSON 段名 `ladders`，键为规范化字符串，
  值形如 `{"type":…,"min":…,"max":…,"tier":"lesser"}`（type 走 `AdditionType.CODEC` 分派）。
- 建造者 DSL「按部位逐阶」：`branch(k).tier(…).tier(…).branch(k2).tier(…).build()`；
  **`BranchBuilder` 必须既有 `branch(String)` 也有 `build()`**（否则转换后的族数据无法连写）。
  `.tier()` 返回 BranchBuilder；`Builder.branches` 为 `Map<String, List<List<Amount>>>`（一个阶层 = 同阶并列的若干条）。
- `Bonus.location` = `Optional<Location>`；codec 用 **`optionalFieldOf` 单参重载**（`MapCodec<Optional<Location>>`）——
  双参重载缺字段时会填默认值，把「无落位」偷换成「有落位」。
- `EssenceFamilies.java`（16 族 / 103 bonus）与 `RuneFamilies.java`（17 族 / 299 bonus）已由脚本 `_tools/convert_families.py`
  从「逐阶声明」改写为「按部位逐阶」（bonus 多重集经 Counter 校验一致）；备份 `_tools/{EF,RF}.orig`。
- 编译坑：`DataResult.error(String)` 不存在 → 用 `DataResult.error(() -> …)`；
  switch 表达式臂里不能 `return` → 抽私有解析方法再 throw。

## 移除 `Location.ENCHANT`（附魔不是词缀）
- 定调：附魔（vanilla ENCHANTMENTS）与符文加成都不是下缀、不占前后缀档位 → 不属于 `Location`；
  `Location` 只剩 `PREFIX` / `SUFFIX`，分层归 `ModLayer`（`ModLayer.ENCHANT` / `RUNE`）。
- 连带改动：词条分桶表的键由 `Location` 改为 **`ModLayer`**（`AttributeApplicator.combineModsAndEnchantments`），
  附魔恒落 `ModLayer.ENCHANT` 桶；新增 `AttributeApplicator.locationBuckets(stack)` 提供**只含前后缀**的
  `Map<Location, …>` 视图（供 `ModNumber` 档位计数口径）。两者分工：全集用于 `setAllMods` 回写（漏一层=丢数据），
  落位视图用于档位计数。
- `EnchantIntegrator.getEnchantMods` 返回 `List<ModifierEntry>`（附魔只有一个层，不需要键）。
- 修掉一个恒不生效的旧逻辑：`ModPoolBuilder.finish` 曾用「附魔侧的落位桶」去取候选池 builder
  （`builders.get(Location.ENCHANT)` 恒空）→ 改为对候选池自身的 `List<Location> location` 逐桶剔除。

## 修 rundata 崩溃：`Element with unknown id: Type[switchCodec=…GemTierProperty…]`
- **现象**：`runData` 在 `ModelProvider$ItemInfoCollector.save` 落盘物品模型时抛
  `IllegalStateException: Element with unknown id: Type[switchCodec=RecordCodec[…]]`，整个 datagen 中断。
- **根因链（已反编译核实，MC 26.2）**：`minecraft:select` 的 `property` 字段走
  `SelectItemModelProperties` 里的 `ExtraCodecs.LateBoundIdMapper<Identifier, SelectItemModelProperty.Type<?,?>> ID_MAPPER`。
  自定义 `SelectItemModelProperty` 若没登记进这张表，`toId` 返回 null →
  `ExtraCodecs.idResolverCodec(…)` 报 `"Element with unknown id: " + <Type 的 toString>`。
  **报错的是编码阶段，所以不是「模型缺失」，而是整个 rundata 挂掉**——排查时极易误判为 datagen 代码本身。
- **正确注册口（有官方事件，不要反射）**：`RegisterSelectItemModelPropertyEvent#register(Identifier, Type<?,?>)`，
  由 `SelectItemModelProperties.bootstrap()` 抛出（NeoForge 补丁）。datagen  JVM 同样会走到：
  `client/data/Main` → `DatagenModLoader.begin(..., () -> ClientBootstrap.bootstrap(), …)`，
  故客户端与 datagen 两条路径共用一次注册。
- **落地**：`GemTierProperty` 加 `@EventBusSubscriber(modid=CraftOfExile.MODID, value=Dist.CLIENT)` +
  静态 `onRegisterSelectItemModelProperty(RegisterSelectItemModelPropertyEvent)`，登记 id `coe:gem_tier`；
  模型里落 `"property": "coe:gem_tier"`（取代旧的 `"property":"minecraft:component"` +
  `"component":"coe:gem_tier"` 那一套，旧形态依赖已删除的 `GEM_TIER` 组件）。
- **同类坑（可复用判据）**：`ConditionalItemModelProperty` / `RangeSelectItemModelProperty` / 自定义 `ItemModel.Unbaked`
  也各自有 `Register*Event` + `LateBoundIdMapper`，机制同构，新建同类自定义元素时一律要先过对应事件登记。
- 26.2 已**无 `SkillTierProperty`**（该实现在 26.x 被移除/改为 `ComponentContents`），别再按旧版本写法套。


## 层级判定返工（三处修正，都是用户当面纠出来的）
1. **「只实现父子级关系，不适用于功能关系」** —— 已作为硬性备注写进 `TagHierarchy` 类 javadoc、
   `LogicalExprs.matches` / `StatTag.buildDescendants` / `StatTag.childrenOf` 的 javadoc。
   功能关系（「火能造成灼烧」这类因果/能力）不进层级表，否则祖先被下位因果反向污染语义。
2. **「火对应灼烧」这个例子是错的** —— `BUILTIN` 实际是 `元素 → {火, 电, 冰, 灼烧, 冰缓, 冰冻, 感电, 电击}`，
   灼烧是**元素的平级兄弟**而非火的子节点。数据本身干净（从没往里写功能关系），错的是 javadoc 里的示范例子，已全部改正。
3. **「不是上限检查，应是重复查询检查」** —— 撤销上一轮加的两处深度上限：
   `StatTag.MAX_HIERARCHY_DEPTH`(8) 与 `TagExpr.MAX_LEAF_DEPTH`(16) 全部删除。
   理由：物品类型树的查询递归本就很深，深度上限会误伤合法数据。
   **终止性改由「重复查询检查」保证**：`path`/`visited` 记录当前路径，回指即停 →
   环不死循环、深链也只走一遍不重复展开。
   - `StatTag`：`pathological`→改名 `cyclic`（只判环，`path` 即当前路径，回指即环），
     环在**加载期**拦下（该条记录整条退回、保留原有取值），运行时不设深度闸。
   - `TagExpr`：不再自带递归，判定本体收进帮助类。
   - 保留 `MAX_DESCENDANTS = 512`（单个父标签后代数上限，防病态扇形展开吃内存——属内存闸，不是深度闸）。

### 帮助方法的归属：通用逻辑收进帮助类，接口只留契约
- 用户定调：「帮助方法应该存在于接口类不要放在实现类」「将通用接口收整到帮助类」。
- **最终形态**：`TagHierarchy` 恢复**纯契约**（只有 `childrenOf` + `supportsProjectionWildcard`），
  default `matches` 全部移除；叶子判定的通用递归收进帮助类
  `data/codec/support/logic/LogicalExprs#matches(TagHierarchy, String, Set<String>)`（及其带 `path` 的递归重载）。
- `TagExpr.matchLeaf` 只留一行转发 `LogicalExprs.matches(resolver, tag, scope)`。
- **结构分工**：`LogicalExpr` = 谓词契约，`LogicalExprs` = 构造/解析/codec/层级解析的帮助类，
  `LeafMatcher` = 维度特小的叶子判定；`TagHierarchy` 保持纯净只描述「关系数据从哪来」。
